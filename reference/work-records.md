# Work records

Express user authorization overrides the workflow defaults in this policy, including record maintenance, prompts, validation, PR creation, and closure gates. Follow it within its stated scope without asking for the same authorization again. Record the override and actual remaining work in the existing execution owner when applicable; preserve accurate validation and integration status. Permission to override a rule is not itself a waiver of every rule for the current task.

Repository docs own lasting product direction, architecture, decisions, current behavior, and evidence. GitHub issues own adopted work: scope, acceptance criteria, dependencies, progress, and preferred model/effort. Link supporting docs rather than duplicating plans.

Draft a tentative plan in conversation or a user-requested location. Move it to tracked work only when the user adopts it and authorizes tracker publication; planning alone does not grant that authority. Name one execution-status owner. Use a parent issue for coordination and executable issues for one coherent, session-sized outcome. Keep future or dormant scope explicitly deferred; activate it when prerequisites and acceptance become concrete.

Read this policy when starting existing tracked work as well as when adopting work or making a handoff. Identify the execution owner and any parent from the existing records before implementation.

At completion and session boundaries update the owning issue; update docs when a decision or behavior becomes established. Close completed work with validation evidence. Superseded or deferred closure is not completion.

Issue closeout follows these defaults unless project instructions or express user authorization specify otherwise:

- For code-delivery issues, create or update and link the PRs needed to bring the required results from all contributing branches into main or the project's designated integration branch, within existing publication authority. Record source branches, relevant commits, target branch, validation evidence, and PR links in the execution owner. Keep the issue open while required review or integration is pending. If publication is unavailable, prepare ready-to-post PR content and identify the unpublished work and available source; do not silently treat branch completion as delivery.
- An intermediate child may close when its explicitly agreed outcome is complete and validated, even if delivery requires later integration. Record its accepted source and remaining integration work in the parent, identify the next responsible issue or mark the integration work unassigned and blocked, and retain the parent's integration gate.
- Before closing a delivery issue or parent as complete, verify that the required results from its contributing branches are present in the target branch and required acceptance checks pass. Link PRs and integration evidence, checking ancestry or equivalent changes where appropriate. Distinguish implemented and tested on a branch, PR awaiting review, and integrated and complete. Research or other issues without repository changes do not require a PR solely to close.

Before reporting completion, closing a child issue, or handing off tracked work, and after any follow-up that changes published continuation source (even after child closure), reconcile the existing records:

1. Keep detailed validation, limits and uncertainty in the sole execution-status owner, linking supporting evidence. This ownership does not suppress parent coordination updates or create another execution owner.
2. If a parent exists, update its current coordination section: maintain a table with one row per child issue and columns for its link, status, and remaining gates or blockers; link the owner's evidence and record relevant branch/commit references. Identify the next ready child and include its current fenced, copyable launch prompt in the parent, with a specific recommended model, supported effort, and rationale outside the fence. The prompt must work without this conversation: name the project, execution owner and parent, accepted continuation source, essential context, prerequisites, bounded outcome, validation, and the requirement to update and read back the owner, parent status and next prompt, and affected dependent instructions before finishing. Follow the model reference and existing session-planning requirements. If no child is ready, explain why; keep any later prompts explicitly provisional until prerequisites are met. A passing subset does not complete the parent or unblock dependent work whose prerequisites remain unmet.
3. Inspect affected dependent launch instructions in existing issues, plans and handoffs; refresh stale prerequisites and source references. For Git continuations, identify the latest accepted prerequisite source and verify it contains the required fixes, using an ancestry check such as `git merge-base --is-ancestor <required-fix-commit> <continuation-ref>` where appropriate. For rebased or cherry-picked fixes, verify equivalent changes and record the evidence. Do not assume an unmerged branch is present on main; name the available source and any remaining integration gate. Keep blocked continuations explicitly blocked.
4. Publish within existing authority and project exceptions; already-authorized maintenance needs no redundant confirmation. Read back published owner, parent and dependent changes before claiming reconciliation is complete. If access or authority is missing, prepare temporary ready-to-post updates, identify exactly which records and changes remain unpublished, and keep the existing owner authoritative. With no parent, reconcile only affected existing records; with no owner, use a temporary update unless a durable record is requested. Do not create issues from tentative planning.

Preserve explicit project exceptions, including document-owned work records and offline trackers. Fit existing paths. Before migration, reconcile active scope and evidence with the proposed owner, replace duplicate status with pointers, and retain historical evidence as dated snapshots. Do not silently reinterpret competing policies or import a project's orchestration rules into this interactive workflow.
