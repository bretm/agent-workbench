# Reusable workflow patterns

These patterns describe reusable workflow choices. Keep concrete project paths, issue details and migration proposals in ignored local reports. Distinguish policy from evidence; do not rank a convention by age or detail.

| Workflow pattern | Stated intention | Shared recommendation |
|---|---|---|
| An issue-owned project converted old plan paths into evidence indexes and explicitly archived broad tasks as unfinished planning | Issues own executable status; docs own lasting evidence | Preserve historical evidence; distinguish deferred closure from completion; activate one concrete session at a time |
| A recent multi-session plan supplies models/efforts but lacks copyable prompts for each session | Human-led development should resume after configuration | Require a fresh-session prompt for every session, with settings outside it and authoritative context linked |
| A completed documentation program retains an active-marked model companion and separate plan/progress owners | Different artifacts serve scope, recommendations and progress | Reconcile status metadata; designate one execution owner and clearly date historical recommendations |
| A project combines issue scope, a document-owned session queue and work-package specifications | Separate scheduling from design and enforce local gates | Keep that division as an explicit project exception until reviewed; do not impose another queue |
| Historical v1/v2 plans are both retained but explicitly superseded/frozen | Preserve narrative and diagnostic evidence | Duplication of filenames alone does not prove competing live authority; keep historical labels and pointers |
| Project hooks and templates contain specialized verification and operating boundaries | Protect local product/infrastructure invariants | Keep commands, evidence tiers, domain maps and guardrails project-local |
| Upstream grilling batches a decision frontier; aliases and multiple handoff variants are globally linked | Thorough probing and transferable context | One portable grilling skill, one question at a time; evidence-based handoff in the existing owner; explicit alias retirement |

The intended baseline is [work-record policy](../reference/work-records.md). Shared agreements carry concise behavior; skills carry procedures. Project configuration carries facts and explicit exceptions. Installation does not migrate document status, close issues, rewrite hooks or decide unresolved policy conflicts.

Fixtures exercise these patterns: document-owned execution exceptions, unresolved duplicate-owner policy, existing import/symlink compatibility, conflicting upstream aliases, outside user edits and changed installed adaptations. Machine discovery remains separate from explicit targeting.
